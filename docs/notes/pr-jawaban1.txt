A.1. ANALISIS vs PREDIKSI — jangan tumpang tindih
--------------------------------------------------------------------------------
Kamu bilang "analisis: rencana menu khusus forecasting harga". Tapi menu
Prediksi SUDAH melakukan forecasting harga (7 hari ke depan, 5 metode).

Rekomendasi: jangan bikin dua menu yang isinya sama. Pilihan:
  (a) HAPUS menu "Analisis", semua forecasting masuk ke "Prediksi".(
      Paling bersih.)
  (b) Pertahankan "Analisis" tapi isinya BERBEDA: analisis LANJUTAN,
      misalnya:
        - Perbandingan harga antar pasar (pasar mana termahal/murah).
        - Deteksi musiman (bulan mana harga cabai selalu naik).
        - Analisis korelasi antar komoditas (harga naik bersama?).
        - Evaluasi hasil intervensi (lihat Bagian E.3).
  Prediksi = "besok berapa?"; Analisis = "kenapa & apa polanya?"

--------------------------------------------------------------------------------
A.2. EWS "kurang terlalu berguna" — apa masalahnya & bagaimana memperbaiki
--------------------------------------------------------------------------------
Penilaian kamu wajar. Masalah EWS sekarang:
  1. Hanya menghitung 2 titik data terakhir (survei terakhir vs sebelumnya).
     Jadi "deteksi anomali" masih sederhana — bukan tren.
  2. Ambang batas (5%/10%/20%) HARD-CODE, tidak bisa diubah pengguna.
  3. Hasilnya baru "daftar", belum sampai "tindakan" (padahal ada menu
     Rekomendasi yang sudah menghubungkan — tapi lemah).
  4. Tidak ada notifikasi otomatis.

Cara membuat EWS lebih berguna:
  (a) Ubah dari "2 titik" jadi deteksi berbasis STATISTIK: bandingkan
      dengan rata-rata + simpangan baku 30 hari (z-score). Jadi bisa
      membedakan "naik wajar" vs "naik abnormal" secara ilmiah.
  (b) Buat ambang batas BISA DIATUR (masuk menu Pengaturan, lihat A.6).
  (c) Perkuat tautan EWS -> Rekomendasi -> (nanti) laporan intervensi.
  (d) Tambah notifikasi (in-app dulu; push/WA nanti).
  Kalau (a)+(b) dikerjakan, EWS naik dari "daftar harga naik" menjadi
  "sistem deteksi anomali yang bisa dipertanggungjawabkan secara statistik".

B.3. RENCANA 2 ENTITAS: USER (viewer/export) & ADMIN (ubah data)
--------------------------------------------------------------------------------
Pertanyaan kamu: "user melihat data & bisa export; admin merubah/
menambahkan data; ada tambahan yang lain??"

Jawaban: rencana ini BENAR dan merupakan langkah wajar berikutnya. Tapi
butuh beberapa komponen. Rinciannya:

1) TABEL USER (belum ada — harus dibuat)
   Model baru di schema.prisma, misalnya:
     model User {
       id       Int    @id @default(autoincrement())
       nama     String
       email    String @unique
       password String            // disimpan dalam bentuk HASH, bukan asli
       role     String            // "viewer" | "admin"
       ...
     }
   Tambah juga relasi ke aktivitas (audit log) — lihat poin 5.

2) AUTENTIKASI (login) — belum ada sama sekali
   Butuh: halaman login, penyimpanan sesi/token, dan middleware yang
   memeriksa apakah permintaan sudah login sebelum akses data.
   Pilihan sederhana: sesi + cookie. Pilihan modern: JWT.
   Password WAJIB di-hash (mis. bcrypt), TIDAK boleh disimpan terbaca.

3) API BARU (POST/PUT/DELETE) — belum ada
   Untuk admin mengubah data, perlu endpoint tulis, misalnya:
     POST   /api/komoditas
     PUT    /api/komoditas/:id
     DELETE /api/komoditas/:id
   Plus proteksi: hanya role "admin" yang boleh akses endpoint ini
   (middleware cek role).

4) HALAMAN FRONTEND BARU
   - Login.
   - Dashboard admin (kelola pasar/komoditas/survei/harga).
   - Viewer: tampilan read-only + tombol export.

5) "TAMBAHAN YANG LAIN??" — yang sebaiknya ikut direncanakan:
   (a) AUDIT LOG: catat siapa mengubah apa & kapan. Penting untuk data
       pemerintah agar bisa dipertanggungjawabkan.
   (b) HAK AKSES GRANULAR: admin penuh vs viewer read-only. Mungkin nanti
       ada "operator" yang cuma boleh input harga harian.
   (c) VALIDASI INPUT: cegah harga negatif/0, tanggal tidak masuk akal.
   (d) APPROVAL/VERIFIKASI: input harga baru masuk "pending" dulu sebelum
       tayang? (opsional, tergantung kebutuhan tata kelola).
   (e) RESET PASSWORD & profil.

ESTIMASI KASAR (untuk perencanaan, bukan janji):
  Login + tabel User + 1 endpoint tulis contoh     : pekerjaan menengah.
  CRUD lengkap semua entitas + audit log + halaman : pekerjaan besar.
  Saran: MULAI KECIL — bikin login + CRUD 1 entitas (mis. harga) dulu
  sebagai pola, lalu perluas ke entitas lain.

  CATATAN JUJUR: saat ini proyek masih "prototipe read-only". Menambah
  user & admin adalah LONJAKAN besar, bukan tambahan kecil. Alokasikan
  waktu khusus.

--------------------------------------------------------------------------------
D.1. "Data hanya 2024, sistem 2026. Cukup untuk EWS? Solusi?"
--------------------------------------------------------------------------------
JAWABAN JUJUR: TIDAK CUKUP untuk EWS real-time HARI INI, karena ada
GAP 2 tahun (2025 & 2026 belum ada). 

Kenapa penting:
  - EWS kita menghitung "perubahan" dari 2 tanggal survei terakhir. Kalau
    data terakhir = 31 Des 2024, maka EWS mencerminkan kondisi AKHIR 2024,
    BUKAN kondisi "hari ini" (2026).

TAPI ini tidak mematikan. Ada beberapa jalan:
  (a) IMPOR DATA TERBARU (paling benar): lengkapi 2025 & 2026 dari SP2KP/
      Bapanas. Kalau diperoleh, EWS langsung "hidup" lagi.
  (b) MODE "AS-OF": sistem menampilkan EWS berdasarkan data terakhir yang
      ADA, dan JUJUR menyebutkan tanggalnya ("kondisi per 31 Des 2024").
      Ini sudah dilakukan — dashboard memang menampilkan "survei terakhir".
      Kelemahan: bukan kondisi terkini.
  (c) BANGUN JALUR INGEST HARIAN: buat mekanisme agar data harian bisa
      rutin masuk (import terjadwal / input manual admin). EWS lalu
      mengikuti data terbaru. Ini arah jangka panjang.
  (d) UNTUK DEMO/PITCH: pakai 2024 sebagai STUDI KASUS bukan klaim
      real-time. Framing: "sistem siap; begitu data terbaru masuk, EWS
      otomatis menyesuaikan."

  RINGKAS: solusinya = (a) dapatkan data 2025/2026, atau (b)+(c) bangun
  jalur ingest rutin. Tanpa itu, EWS hanya menggambarkan 2024.

--------------------------------------------------------------------------------
D.2. "Modelling sekarang pakai apa? Sebaiknya bagaimana?"
--------------------------------------------------------------------------------
MODELLING SAAT INI (faktual, dari kode prediction.ts):
  - Linear Regression (regresi garis lurus).
  - Moving Average 7 hari.
  - Exponential Smoothing (alpha = 0.3).
  - BLEND: gabungan tren LR + harga terakhir (bobot bergerak).
  - Diuji dengan BACKTEST walk-forward, diukur MAPE & RMSE.

HASIL NYATA (contoh Cabe Merah Besar, uji 7 hari terakhir Des 2024):
    Naive (besok = hari ini)      MAPE 3,31%   <- paling akurat
    Exponential Smoothing         MAPE 6,61%
    Moving Average (7 hari)       MAPE 7,60%
    Linear Regression             MAPE 72,13%  <- meleset jauh
    Blend (dipakai sistem)        MAPE 38,59%
  Artinya: untuk komoditas ini, model sederhana MENANG. LR kacau karena
  harga cabai naik-turun tajam (musiman), sedangkan LR menganggap garis
  lurus.

SEBAIKNYA BAGAIMANA (roadmap, urut prioritas):
  1. PERBAIKI BLEND yang sekarang kalah dari Naive. Blend terlalu
     membebani LR. -> Beri bobot adaptif per komoditas, atau minimal
     pilih otomatis metode terbaik hasil backtest per komoditas.
  2. Pilih MODEL PER KOMODITAS (bukan satu model untuk semua). Bawang
     beda perilaku dari cabai. Simpan "metode terbaik" tiap komoditas.
  3. TANGANI MUSIMAN: model yang sadar musiman (mis. SARIMA, atau
     Prophet dari Facebook) bisa jauh lebih baik untuk harga pangan
     yang selalu naik jelang Ramadan/Lebaran.
  4. Naikkan KUALITAS DATA dulu (lihat C.1) — model sebagus apa pun
     akan tersandung data bolong.
  5. PERTIMBANGKAN faktor eksternal (musim panen, hari besar) sebagai
     variabel tambahan.
  RINGKAS: sekarang sudah punya KERANGKA yang jujur (backtest). Langkah
  berikutnya = pemilihan model per komoditas + model musiman + data lebih baik.

JAWABAN: mungkin, dalam bentuk "NEAR-REAL-TIME" (hampir real-time), bukan

--------------------------------------------------------------------------------
E.1. 3 STATUS (aman, waspada, intervensi)
--------------------------------------------------------------------------------
Sekarang sistem pakai 4 level: Normal, Siaga, Waspada, Kritis.

Usulan 3 status kamu (aman / waspada / intervensi) sebenarnya LEBIH BAIK
untuk pengambilan keputusan, karena langsung mengarah ke TINDAKAN.
Pemetaan yang disarankan:
    Normal  (<5%)              -> AMAN
    Siaga (5-10%)              -> AMAN/waspada (zona abu-abu)
    Waspada (10-20%)           -> WASPADA
    Kritis (>20%)              -> INTERVENSI
Rekomendasi: pakai 3 status untuk TAMPILAN (ringkas, tindakan-oriented),
tetapi pertahankan 4 level di perhitungan internal agar transisi tetap
halus. Ini juga menyelaraskan EWS dengan menu Rekomendasi (intervensi).

Kamu menyinggung "data kebijakan pemerintah". Penting untuk jujur soal batas:
  1. WEB INI ALAT BANTU, BUKAN PENGGANTI KEBIJAKAN. Sistem menyajikan
     data & prediksi; keputusan tetap di tangan pengambil kebijakan.
  2. PREDIKSI = PERKIRAAN, BUKAN KEPASTIAN. Sudah diukur dengan MAPE
     (rata-rata meleset). Angka ini harus ditampilkan agar tidak
     disalahartikan sebagai kebenaran mutlak.
  3. TIDAK SEMUA FAKTOR MASUK MODEL. Kebijakan pemerintah (operasi pasar,
     subsidi, impor) MENGUBAH harga secara mendadak — hal yang tidak
     bisa ditangkap model statistik dari data historis saja.
  4. KUALITAS DATA MEMBATASI KUALITAS ANALISIS (lihat C.1).
  5. Sistem SEBAIKNYA menyertakan disclaimer: "prediksi bersifat
     indikatif, keputusan berdasarkan pertimbangan menyeluruh".
  Ide lanjut: masukkan VARIABEL KEBIJAKAN sebagai catatan/timeline di
  web, supaya lonjakan harga bisa dijelaskan ("naik karena menjelang
  Lebaran" atau "turun setelah operasi pasar").
