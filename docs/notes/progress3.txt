BAGIAN 1 — LATAR BELAKANG PROYEK
================================================================================

1.1. APA ITU SIMONPEDIA
--------------------------------------------------------------------------------
SIMONPEDIA (Sistem Monitoring dan Prediksi Harga Bahan Pokok) Bapok Surabaya
adalah aplikasi web untuk MEMANTAU HARGA BAHAN POKOK di Kota Surabaya, dan
mengubah data harga tersebut menjadi tiga hal yang berguna untuk pengambilan
keputusan:

  1. PERINGATAN DINI  — komoditas mana yang harganya bergerak abnormal (EWS)
  2. PREDIKSI         — ke mana harga bergerak 7 hari ke depan
  3. REKOMENDASI      — tindakan apa yang sebaiknya dilakukan

Pengguna sasaran: petugas dinas pangan / pemantau harga / pengambil kebijakan
di lingkungan Pemerintah Kota Surabaya. Sistem ini adalah ALAT BANTU
KEPUTUSAN, bukan pengganti kebijakan.

Asal-usul: proyek berawal dari frontend React yang seluruh datanya masih
hardcoded/dummy dan memakai backend online (Supabase). Lalu dimigrasikan
menjadi sistem penuh dengan backend sendiri + database sendiri, memakai
data REAL Bapanas/SP2KP.

1.2. KONDISI AWAL & MIGRASI
--------------------------------------------------------------------------------
- Awalnya 8 halaman React, semua data hardcoded/dummy, tanpa database.
- Backend memakai Supabase (online).
- Migrasi (Task 1): hapus Supabase → bangun server sendiri:
    Express 4 + Prisma 6 + PostgreSQL 18 (TypeScript).
  (Express sengaja v4, bukan v5 — v5 ada breaking change di Router.)
- Frontend diubah agar mengambil data via REST API, bukan langsung DB.

1.3. ROADMAP ASLI (dari task1.txt)
--------------------------------------------------------------------------------
  Task 1 — Migrasi Supabase → backend sendiri + PostgreSQL + REST API dasar
  Task 2 — Early Warning System (deteksi anomali → level risiko → rekomendasi)
  Task 3 — Prediksi harga
  Task 4 — Modul Urban Farm (petani, lahan, panen, produksi)
  Task 5 — Integrasi SIMONPEDIA dengan Urban Farm

Alur data yang dicita-citakan:
  Pasar → Survei → Detail Survei → Komoditas → Harga → Dashboard/Grafik

Arsitektur target:
  React + TypeScript → REST API → Node.js + Express + TypeScript
  → PostgreSQL → (nanti) Modul Urban Farm

BAGIAN 2 — RUMUSAN MASALAH
================================================================================

2.1. MASALAH UTAMA
--------------------------------------------------------------------------------
Data harga bahan pokok sebenarnya SUDAH ADA (dari survei pasar harian), tetapi:

  1. TERSEBAR   — tersimpan di file Excel/berkas terpisah per bulan,
     tidak terpusat.
  2. PASIF      — hanya berupa DERET ANGKA. Tidak memberi tahu "apa yang
     harus dilakukan", tidak menghitung risiko, tidak memperkirakan
     arah harga berikutnya.
  3. LAMBAT DIKETAHUI — kalau menunggu laporan/analisis manual, lonjakan
     harga (mis. cabai naik 22% dalam sehari) baru diketahui setelah
     terlambat untuk intervensi cepat.

2.2. RUMUSAN MASALAH
--------------------------------------------------------------------------------
"Bagaimana mengubah data harga bahan pokok yang tersebar dan pasif menjadi
informasi yang PROAKTIF dan dapat ditindaklanjuti — berupa peringatan dini,
prediksi arah harga, dan rekomendasi tindakan — untuk mendukung pengambilan
keputusan intervensi pasar di Kota Surabaya?"

2.3. PERTANYAAN PENELITIAN (turunan)
--------------------------------------------------------------------------------
  a. Komoditas mana yang harganya bergerak abnormal, dan seberapa bahaya?
     (dijawab oleh EWS)
  b. Ke mana harga bergerak 7 hari ke depan? Seberapa akurat perkiraannya?
     (dijawab oleh Prediksi + backtest)
  c. Tindakan apa yang disarankan untuk tiap kondisi risiko?
     (dijawab oleh Rekomendasi)

2.4. BATAS KEMAMPUAN (JUJUR)
--------------------------------------------------------------------------------
Penting dipahami sejak awal (lihat juga pr-jawaban1.txt Bagian E.4):
  1. Sistem ini ALAT BANTU, bukan pengganti kebijakan pemerintah.
  2. Prediksi = PERKIRAAN, bukan kepastian — diukur dengan MAPE (rata-rata
     % meleset) dan ditampilkan apa adanya.
  3. Tidak semua faktor masuk model: kebijakan pemerintah (operasi pasar,
     subsidi, impor) mengubah harga secara mendadak dan tidak bisa
     ditangkap oleh model statistik dari data historis saja.
  4. Kualitas data membatasi kualitas analisis (lihat BAGIAN 3 & 5).

3.1. KENDALA DATA
--------------------------------------------------------------------------------
a. DATA KURANG LENGKAP (~14% sel harga kosong di file sumber SP2KP).
   - Kekosongan STRUKTURAL: tidak semua pasar menjual semua komoditas.
   - Contoh (Januari 2024): 33 komoditas lengkap di 7 pasar; 26 komoditas
     hanya di 1-6 pasar; 1 komoditas (Beras Medium) kosong di semua pasar.
   - Nilai kosong di file sumber: "-", 0, "", "#DIV/0!".
   - Ini BUKAN bug sistem, melainkan batasan sumber data.
   - Penanganan sistem: rata-rata dari pasar YANG MELAPOR saja + simpan
     field 'jumlahPasar' agar transparan.
   - Detail lengkap + usulan solusi ada di progress2.txt BAGIAN 5, dan
     daftar pertanyaan konkret untuk divisi analisis juga di sana.

   "hari ini" 2026. EWS kita menghitung perubahan dari 2 survei terakhir,

     menyebut tanggal data, sudah dilakukan di Dashboard), atau

BAGIAN 6 — METODE
================================================================================

6.1. EARLY WARNING SYSTEM (EWS)
--------------------------------------------------------------------------------
EWS menjawab: "komoditas mana yang harganya bergerak ABNORMAL?"

Langkah backend (server/src/routes/ews.ts):
  1. Ambil HANYA 2 tanggal survei TERAKHIR (bukan seluruh baris) → cepat.
  2. Hitung rata-rata harga per tanggal (dari pasar yang melapor).
  3. Hitung: persenPerubahan = (rataBaru − rataLama) / rataLama × 100
  4. Tentukan LEVEL dari nilai MUTLAK perubahan:
       < 5%    → NORMAL   (aman)
       5-10%   → SIAGA    (mulai waspada)
       10-20%  → WASPADA  (perlu tindakan)
       ≥ 20%   → KRITIS   (darurat)
  5. Level ≠ Normal → buat ALERT per pasar.
  6. Susun ringkasan: jumlah komoditas per level.

Kenapa threshold 5/10/20%? Praktik umum pemantauan harga pangan:
pergerakan harian < 5% wajar, > 20% berarti gejolak serius.
(Usulan lanjutan: deteksi berbasis z-score + ambang bisa diatur.)

6.2. PREDIKSI HARGA
--------------------------------------------------------------------------------
Empat langkah:
  1. SIAPKAN DATA: satu harga per hari = rata-rata pasar (noise hilang).
  2. TIGA METODE dihitung berdampingan:
     a. Linear Regression — pasang garis lurus; slope = kecepatan
        naik/turun (Rp/hari).
     b. Moving Average 7 hari — rata-rata jendela mingguan; menenangkan
        fluktuasi.
     c. Exponential Smoothing (α=0,3) — rata-rata berbobot yang lebih
        menghargai hari terbaru.
  3. BLEND (metode produksi): campuran tren LR + harga terakhir; hari
     dekat lebih percaya harga hari ini, hari ke-7 lebih percaya tren.
  4. BACKTEST (uji kejujuran): sembunyikan 7 hari terakhir, latih pada
     data sebelumnya, suruh menebak 7 hari tersembunyi, hitung melesetnya.
     Metrik: MAPE (%) dan RMSE (Rp). Baseline: Naive (besok = hari ini).

6.3. TEMUAN JUJUR DARI BACKTEST
--------------------------------------------------------------------------------
Contoh nyata (Cabe Merah Besar, uji 7 hari terakhir Des 2024):
  Naive (besok = hari ini)      MAPE 3,31%   ← paling akurat
  Exponential Smoothing (a=0.3) MAPE 6,61%
  Moving Average (7 hari)       MAPE 7,60%
  Linear Regression             MAPE 72,13%  ← meleset jauh
  Blend (dipakai sistem)        MAPE 38,59%
  Akurasi terukur Blend: 61,4%

Artinya: untuk komoditas ini, model SEDERHANA menang. Ini TIDAK
disembunyikan — halaman Prediksi menampilkan tabel backtest + PERINGATAN
otomatis bila Blend kalah dari Naive. Field 'confidence' lama yang dulu
angka buatan sudah DIGANTI akurasi terukur (100 − MAPE).

Kenapa LR kacau? Harga cabai naik-turun tajam (musiman: naik jelang
Ramadan/Lebaran), sedangkan LR menganggap tren lurus → ekstrapolasi meleset.

Roadmap metode (prioritas): perbaiki Blend (bobot adaptif) → pilih MODEL
PER KOMODITAS → model sadar-musiman (SARIMA/Prophet) → tingkatkan kualitas
data → masukkan faktor eksternal (musim panen, hari besar).
